YOBO — Account Aggregator Platform

A consent-based Account Aggregator letting users securely link accounts across banks and share a real-time view of their data — where consent-revocation timing is the single most safety-critical test surface.

Overview

YOBO is a consent-based Account Aggregator (AA) — it lets a user link accounts across multiple banks (FIPs) and share a real-time, machine-readable view of that data with an app or lender (FIU) they trust, without ever owning the underlying data itself. Every data share is governed by an explicit, revocable consent artifact.

In plain terms, YOBO is a secure, revocable "data-sharing remote control" — instead of a user handing over net-banking credentials or emailing bank statements to a lender, they approve a scoped, time-bound consent that can be switched off at any moment. The module is composed of a focused set of consent-and-data-flow services:

How It Works & My Role

Core Consent Flow

  1. User links an account via a Bank (FIP) — linking alone shares no data
  2. An FIU requests consent (purpose, data types, date range, duration — fully explicit)
  3. User approves; consent becomes Active, data flows per the approved scope
  4. User can revoke anytime — data sharing stops immediately
  5. Consent also expires automatically once its duration elapses

Why Revocation Timing Is the Central Risk

The window between a user clicking Revoke and data actually stopping is the product's single most safety-critical test surface — an in-flight fetch must never complete after revocation, only ever before it.

Challenges & Problem-Solving

Two representative problems from this module — how they were found and resolved, not just what the final test covered.

Data continuing to flow after a revocation
Challenge

A data fetch already in progress when a user revoked consent completed anyway, delivering data to the FIU after the user had explicitly revoked access.

Approach

Designed a timing-based test that deliberately revoked consent mid-fetch, rather than only testing revocation strictly before or after a complete fetch cycle.

Outcome

Filed as BUG-YOBO-3011 (Critical); the fix added a revocation check immediately before data handoff, not just at fetch initiation.

Revoked and Expired consents looking identical
Challenge

Revoked and Expired consents were visually indistinguishable in Consent History, making it impossible to tell a deliberate user action from a passive timeout.

Approach

Treated this as a compliance-relevant defect rather than a cosmetic one, since AA regulations expect a transparent, auditable consent record.

Outcome

Filed as BUG-YOBO-3024; the fix introduced distinct status values and UI treatment for each.

Key Achievements

  • Designed a consent-revocation-focused regression suite treating in-flight-fetch timing as a first-class, highest-priority scenario
  • Validated consent artifact transparency — purpose, data types, date range, and duration always explicit before approval
  • Verified cross-FIP consistency, treating bank-integration variability as its own dedicated test dimension
  • Logged and tracked defects across consent-lifecycle and UI-consistency themes
