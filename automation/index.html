Paywize Automation Testing Framework

A Hybrid test automation framework (Page Object Model + Data-Driven Testing + API Mocking) built to test the Paywize fintech admin dashboard — written so someone with zero prior context can read it top to bottom and understand exactly what exists, why it's built this way, and what it has already found.

What This Project Actually Is

Paywize is a live fintech admin/merchant dashboard. This repository is an automated test suite that logs into it like a real user, clicks through every module (Payout, Collection, Connected Banking, Reports, and more), and checks that things behave correctly — instead of a human manually clicking through the same 120 checks every time something changes.

Why "Hybrid" and Not Just POM?

The industry term for this framework's design is Hybrid — not "just Page Object Model." Three separate patterns are deliberately layered together, each solving a different problem.

01 · LOCATE

Page Object Model

Every screen is a class with methods like clickAndValidateUrl(...). Tests call the method — they never touch a raw element directly.

02 · LOCALIZE

Data-Driven Testing

Selectors and expected values live in external JSON, not inside the code. A drifted selector or changed number is a JSON edit, not a code change.

03 · SIMULATE

API Mocking

When a test needs an exact, guaranteed number to assert against, the real network response is intercepted and swapped for a fake, predictable one.

"Locate. Localize. Simulate."

Why not just plain POM? Three real bugs from this repo are the proof

"Locate" saved us

Merchants' badge selectors matched "Active" inside "Inactive" (a substring collision). Fix = edit 7 lines in one JSON file. In plain POM that's opening a class and editing logic across 7 methods — much riskier.

"Localize" saved us

Connected Banking's real URLs (/transactions, /lien) turned out different from our guesses. Fix = a 2-line JSON edit, zero code touched.

"Simulate" saved us

Dashboard's Collection amount changes constantly on the live site — you can't assert against a moving number. Mocking the API freezes it so the assertion is even possible.

The interview-ready line: "Hybrid — POM for structure, Data-Driven for values, Mocking for predictability — because this is a live, evolving fintech product, not a toy app."

The Engine Room — src/core

Five files do all the repetitive plumbing so every Page Object and test stays thin. Each one powers exactly one pillar above — you build on these, you almost never edit them.

WebUtil.js — LocateWraps every raw Playwright action (click, fill, getText, waitForUrl…) with logging, timeouts, readable errors.
SelectorManager.js — LocalizeReads locators/PageSelectors.json once, caches it, hands back one page's selectors by class name.
TestDataManager.js — LocalizeReads test-data/**/*.json by test name; resolves login credentials via Config.js's env-var table.
CommonUtil.js — SimulatemockApiResponse() / removeMock() — intercepts/restores network calls via page.route().
PageManager.js — FacadeOne object (sharedPages) exposing every Page Object as a lazy getter, plus test-data shortcuts.
The One Sequence Worth Remembering

Every Page Object method starts with await this.ensureSelectors(). That awaits a promise the constructor already kicked off — instant after the first call, but skip it and this.selectors might still be empty when your method reads it.

How One Test Actually Runs

Trace this once for should validate dashboard collection amount and every other test in the repo follows the same shape.

  1. Playwright loads the saved session (.auth/admin.json) — the browser opens already logged in.
  2. The spec registers a mock: commonUtil.mockApiResponse(url, dashboardCollectionMock) — "if the page asks for this URL, return fake JSON instead."
  3. The spec reloads the page — the app's real frontend code fires its real API call.
  4. Playwright intercepts that exact call and returns the fake JSON from step 2.
  5. dashboardPage.validateCollectionAmount(expected) runs: loads selectors → reads the DOM text → compares to the expected value.
  6. Test passes or throws a descriptive error based on that one comparison.

Every test = mock → reload/navigate → call a Page Object method → compare against test data. Once this clicks, every spec file in the repo reads the same way.

Real example — Payout's tab-click check (PayoutPage.js + PageSelectors.json):

Hybrid — Page Object never sees a raw selector 
// pages/admin/payout/PayoutPage.js
async clickAndValidateUrl(clickSelectorKey, expectedUrlPart) {
  await this.ensureSelectors();
  await this.webUtil.waitAndClick(
    this.selectors[clickSelectorKey]
  );
  await this.webUtil.assertUrlContains(expectedUrlPart);
}
// locators/PageSelectors.json
"payoutTab": "//div[@role='tablist']//div[
  normalize-space()='Payout']"
// test-data/admin/payout/PayoutTestData.json
"should update URL when clicking Payout tab": {
  "expectedUrlPart": "tab=payout"
}
Plain POM — same behavior, all inlined 
// pages/admin/PayoutPage.js
class PayoutPage {
  constructor(page) {
    this.page = page;
    this.payoutTab = page.locator(
      "//div[@role='tablist']//div[" +
      "normalize-space()='Payout']"
    );
  }
  async clickPayoutTab() {
    await this.payoutTab.click();
  }
}
// test-cases/admin/payout/payout.spec.js
test('should update URL when clicking Payout tab',
  async ({ page }) => {
    const payoutPage = new PayoutPage(page);
    await payoutPage.clickPayoutTab();
    expect(page.url()).toContain('tab=payout');
    // ← hardcoded, not loaded from JSON
});

Functionally identical result either way. The difference is entirely where the volatile stuff lives — inside code (POM) or externalized to JSON (Hybrid).

What each approach costs you when something changes

Change neededPlain POMHybrid (this repo)
A selector breaksOpen the class, edit code mixed with logicEdit one line in PageSelectors.json
An expected value changesEdit the test file directlyEdit one line in test-data/
Need a predictable number to assert onWrite ad-hoc interception inline, per testAdd one fixture JSON + one mockApiResponse() call
Add a whole new pageOne big file: locators + logic + assertions togetherSplit cleanly across 4 files, each with one job
Plain POM Isn't Wrong

It's simpler to learn first, and plenty of real teams use it exactly as-is for smaller projects. Hybrid earns its extra folders specifically because Paywize is a live, evolving fintech product with multiple roles and 120+ test cases, not a toy app — see the 3 real-bug proofs above for why that trade paid off here.

2 Real Bugs Found in the Live Product

Genuine defects in Paywize itself, reproduced consistently across multiple runs — not test flakiness, not framework issues. Both are kept visible in every test report rather than silently worked around.

Rendering BugMerchants module

"New Request" filter under-renders its own labeled count

Clicking the New Request stat card correctly updates the total count (622 → 290), and the pagination label still claims "Showing 1–10" — but only 8 rows actually render in the DOM. All 8 rendered rows do show the correct status, so it's specifically a rendering bug, not a wrong-status filter bug. Reproduced across 3 separate runs.

UI InconsistencyReports module

GST Statement (Payout) is missing its "Showing X of Y" label

Every other paginated table in the app shows a records-count label next to its pagination controls. GST Statement (Payout)'s CSB and SIB tabs render the pagination buttons but leave that label completely blank — reproduced on both tabs. Documented as two tests that intentionally fail, so it shows up red in every report until fixed.

Why a 3-Way Check Mattered

The Merchants bug was first suspected to be a "wrong status" bug. A simple label-vs-status check couldn't tell "under-rendered" apart from "wrong data" — only checking labeled count → actual DOM row count → matching-status count together correctly pinpointed which failure class it really was.

Also caught along the way (framework/assumption fixes, not product bugs)

Wrong URL-slug guesses — Connected Banking's assumed all-transactions/lien-management were actually transactions/lien. Caught by the failing assertion printing the real URL.
Account lockout, not a flake — a fixed-phone-number negative login test tripped the site's own anti-brute-force lockout after repeated runs. Fixed by accepting either error message as valid.
Our own dashboard's count mismatch — the Visual QA Dashboard's reporter silently excluded the setup login step from its own totals, a 1-test gap vs. Playwright's report.
Wrong tab-selector guess — Team Management's Internal/External tabs were guessed as buttons; they're actually the same tablist pattern every other module uses.

Q&A Library

Every question that's come up while building this, answered using this project's real code and real bugs — never a generic textbook example.

Framework Basics
What kind of framework is this, in one line?

A Hybrid Test Automation Framework — Page Object Model + Data-Driven Testing + API Mocking — built on Playwright with JavaScript, covering the Paywize admin (and paused merchant) dashboards.

If this were plain POM instead, what would actually change?

Two folders disappear entirely — locators/ and test-data/ — because their contents would move directly inside each Page Object class and each test file. The fixtures/*Mock.json API-mocking layer would also vanish, since mocking isn't part of POM at all. Same real behavior, just everything volatile moves from JSON back into code.

Of the three layers, which is safest to drop under time pressure?

API Mocking. Merchants, Payout, and Connected Banking were all built with zero mocking and validate real end-to-end behavior (URL changes, real filter clicks) — that's exactly how the real Merchants bug and the Connected Banking URL mistakes were caught. Mocking only matters when you need one exact, stable number to assert against. POM and Data-Driven are load-bearing for every test; dropping either makes the whole thing harder to maintain immediately.

What does the folder structure look like, and why?

pages/ = what you edit most (Page Objects) · locators/ = every selector, centralized · test-data/ = every expected value, centralized · fixtures/ = mocks + shared setup · test-cases/ = the actual test files · src/core/ = framework internals, rarely touched. The idea: add a new test by editing 2–3 JSON/JS files, never opening src/core/.

Running Tests
How do I run everything, headless vs. headed?
npx playwright test              # headless (default, fastest)
npx playwright test --headed     # headed — watch the browser
How do I run just a specific set of modules — e.g. only Dashboard, Payout, and Connected Banking?

Every module carries a tag. Join tags with | (regex OR) in --grep:

npx playwright test --project=admin-setup --project=admin \
  --grep "@dashboard|@payout|@connectedBanking"
Is parallel execution possible? How many workers can I use?

Yes — fullyParallel: true is set, but the actual concurrency is controlled by workers (src/config/Config.js, override with WORKERS=<n>). Parallelism happens per spec file, not per test — tests inside one file share a page and always run in order. There's no hard cap, but pushing workers too high is bounded by your own machine, not the framework: testing at WORKERS=6 on an 8-core/16GB machine already under memory pressure caused the very first login to time out. Settled on workers: 1 (sequential) as the safe default; override deliberately when you actually want a parallel or load test.

If a test fails, how do I find out why?

In order: read the console output (every action logs what it did) → check the auto-saved failure screenshot → open the HTML report (npx playwright show-report) → re-run with --headed to watch it live → open a saved trace (npx playwright show-trace) for a full scrubbable timeline.

Regression Testing Terminology
What's the difference between Retesting, Partial Regression, Sanity, and Full Regression?

Retesting — confirming the exact reported defect is fixed. Example: Connected Banking's URL was assumed all-transactions, really transactions — retesting is re-running that one "click, verify URL" scenario after the fix.

Partial Regression — re-checking the surrounding area of that same module. After fixing that one link, it means re-checking the rest of Connected Banking's Quick Links and cards, since they share the same page/component.

Sanity Testing — a quick, shallow pass across major flows right after a new deploy, to decide if it's stable enough for deeper testing. About depth, not size — e.g. a fast pass through Login → Dashboard → Payout → Connected Banking, not the full suite.

Full Regression — re-running the entire suite across the whole app. Reserved for major releases or architecturally significant changes (an auth rework, a shared component upgrade) — not just because one module happens to be large.
